# Enhancement Three: Databases

## Describing the Artifact

The artifact is the Contact Service, the same Java application I originally built in CS-320 (Software Testing, Automation, and Quality Assurance) that Enhancement One turned into a working command-line application and Enhancement Two rebuilt around a HashMap and a sorted ArrayList for fast lookups and searching. Enhancement Three starts from Enhancement Two's completed state. Every contact still only existed in memory going into this enhancement, so closing the program meant losing everything a user had entered.

## Justifying Its Inclusion

I picked this artifact for the databases category because it had no persistence at all going into this enhancement. Enhancement Two made every operation on Contact Service fast, but none of that mattered once the program actually closed, since nothing survived past the process ending. Adding persistence to the program is a perfect enhancement for this category.

I added SQLite through JDBC as a write-through layer sitting behind the HashMap and sorted ArrayList Enhancement Two already built, without replacing those structures or querying the database directly for every operation. getContact, listAll, and searchByName still read only from the in-memory cache, so none of Enhancement Two's complexity guarantees changed. Only add, delete, and the four update methods now also write through to the database.

ContactService can be constructed two different ways. The no-arg constructor opens a private, in-memory SQLite database that exists only for the life of that instance. That is what every test written before this enhancement still uses, so all of them stayed isolated and passed unmodified. A new ContactService(String databaseFilePath) overload opens a real file instead. That is what ContactApp actually uses now, and it is also what let me open two separate instances against the same file to prove data survives a restart.

Add and delete write to the database first, before touching either in-memory structure, so a failed write never leaves the cache holding something the database doesn't actually have. The four update methods can't follow that same order cleanly, since Contact's setters validate and mutate a field in the same step. There is no way to confirm a new value is valid without already having changed it. Instead they mutate the field, attempt the database write, and roll the field back to its previous value if that write fails, so the cache and the database still agree with each other either way.

Every database write uses a parameterized PreparedStatement, with every value bound as data rather than built into the SQL string, which is the actual mechanism that prevents SQL injection. SQLException is a checked exception, but every existing ContactService method is unchecked, so I added a new ContactPersistenceException that wraps it. That kept every existing method's signature exactly the same, without forcing try/catch or throws onto callers that predate this enhancement, including the entire existing test suite.

On startup, ContactService also reads the highest existing numeric id already in the database and resumes its id counter from there rather than always starting back at 1, so reopening a database with existing contacts can't hand out an id that already belongs to one of them.

## Reflecting on the Process

The biggest design decision in this enhancement was figuring out what order to do things in for add, delete, and the four update methods. Add and delete were straightforward because the object being written is already fully valid by the time either method runs, so writing to the database before touching the cache was a safe order. The four update methods forced a different approach. Since Contact's setters validate and mutate a field together, there was no way to check if a new value was valid without already having applied it. What I learned from working through that is that a consistency guarantee has to fit the actual shape of the code it protects. The same fail-safe order that worked cleanly for add and delete needed rework once setters that combine validation and mutation were involved: mutate first, then write, then roll back on failure.

Running the code against a real database file turned up a problem as well. The first tests that opened a database file passed on their own, but the temp directory JUnit was supposed to clean up afterward failed to delete with a Windows error saying the database file was still in use by another process. Nothing had ever closed the underlying JDBC connection, so the file stayed locked for as long as the test process was alive. I added a close() method and made ContactService implement AutoCloseable, and that fix turned out to be useful twice. It solved the actual file-lock problem, and it also gave me a clean way to test the failure and rollback paths afterward. Closing the connection first and then calling an operation throws a SQLException, so no mocking or test-only hook needed to prove ContactPersistenceException and the rollback logic actually work.

Coverage testing revealed something even more specific once the ID counter resume logic was in place. A branch inside it, the case where a row's id turns out to be numerically smaller than the running highest id already seen, never showed as covered no matter what order I inserted contacts in. My first attempt at testing this used the ids "50" and "1" assuming SQLite would scan them back in the order they were inserted, but it didn't expose the gap at all. The actual explanation was not about insertion order. The ID column is a TEXT PRIMARY KEY, and a query that only selects that column can be answered directly from the primary key's index in string order rather than insertion order. String-wise, "1" sorts before "50" the same way it does numerically, so both of my test IDs happened to come back in an order where the running maximum only ever grew, no matter which order I inserted them in. Once I picked two IDs where string order and numeric order actually disagree, "2" and "10", since "10" sorts before "2" as a string but is the larger number, the branch finally ran for a real reason instead of running out of test cases to try.

One limitation I would like to point out is what happens if more than one instance of ContactService were ever running against the same database at the same time. Reading the highest existing id once at startup and incrementing a local counter from there only works safely for a single running instance. Two instances running concurrently would each compute their own starting point independently and could hand out colliding ids, since neither one rechecks the database as it goes. I handle this differently at work, where we have multi-user and multi-instance services working against the same databases. There, our standard is to generate a unique id at the moment of insertion, inside the same stored procedure doing the insert, so the database itself is the single point of coordination instead of every caller keeping its own separate counter. ContactService's scheme is correct for what this artifact actually is, a single-user desktop application where only one instance is ever running, but a system built to run multiple instances against the same database would need a database-side approach or a centralized id service instead.
