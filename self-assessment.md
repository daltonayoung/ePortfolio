# Professional Self-Assessment

Completing this Computer Science program, and building this ePortfolio around it, have sharpened what I actually bring to a team beyond writing code that works. Coursework gave me the formal foundation, and this capstone gave me a chance to apply that foundation to one real, evolving piece of software across three different lenses. Between the program and my current work as a developer, I've built a set of strengths I can point to directly and showcase in this ePortfolio.

Collaborating in a team environment is something I learned formally in this program and then had to actually put into practice on the job. CS-310, Collaboration and Team Project, was one of the most directly useful courses I took, since it's where I learned Git in real depth through branching, merging, resolving conflicts, and workflow strategies like git-flow. I applied that directly on the job by helping move my team toward a more structured Git-flow style of source control, which improved how we collaborate on a shared codebase instead of everyone stepping on each other's changes. The same discipline shows up in this capstone through staged commits with messages that explain why a change was made, so a teammate reviewing the history later can actually follow the reasoning behind it.

Communicating with stakeholders is something I first practiced formally in CS-250, Software Development Lifecycle, where I rotated through Scrum roles on a simulated project and had to write clear, direct requests to teammates in the Product Owner and Tester roles for information I needed, while still leaving room to meet and talk it through further. I've had to do the same thing for real since then. I recently worked closely with our Customer Service department on a new order entry screen built to replace a cumbersome SAP Fiori workflow. The module uses OCR and AI to translate a customer's purchase order into a sales order that's ready to submit, often requiring only minor tweaking from the CSR and sometimes none at all. I worked directly with the CSR manager and specific team members who specialize in different sales channels throughout the design and implementation. I changed the approach based on their feedback and took their suggestions seriously instead of just building what I thought they needed. The same instinct of letting the people who actually use the software shape it is behind decisions like Enhancement One's field-by-field validation in the command-line interface, which catches a mistake the moment it happens, not after an entire form has been filled out.

Data structures and algorithms are where I learned to stop treating "it works" as the finish line. In CS-260, Data Structures and Algorithms, my final project implemented the same bid-tracking problem three separate ways: a vector, a hash table with chaining, and a binary search tree, then compared them directly instead of assuming one structure was good enough for everything. The comparison used real numbers, not vague intuition. A binary search tree search across 10,000 records tops out around 14 comparisons in the worst case, O(log n), against a linked list's potential 10,000, O(n). Enhancement Two of this capstone is where that same reasoning showed up again years later. I chose a HashMap for one access pattern and a sorted structure searched with binary search for another, rather than forcing a single structure to serve every need. I can also state precisely why each operation costs what it costs.

Software engineering and database work make up most of what I actually do day to day. Database design and management was one of the three most important skills I developed in this program, and it has stayed central to my daily work ever since. I write and maintain SQL and stored procedures most days of the week. In CS-340, Advanced Programming Concepts, I built a full-stack example of that same discipline: a Python and Dash dashboard backed by a MongoDB database, with a portable CRUD module I wrote from scratch using PyMongo instead of scattering database calls throughout the application. Enhancement Three of this capstone extended that further into application-level persistence by designing a write-through cache backed by SQLite through JDBC instead of bolting a database onto existing code without thinking about how the two should actually stay in sync.

Security is a mindset I first practiced in IT-201, Computer Platform Technologies, designing access control for a fictional company around Active Directory security groups, NTFS permissions, and the Principle of Least Privilege, restricting each user to exactly the access their role actually needed. I've applied that same principle in a production environment since then. I integrated our internal systems with Entra ID single sign-on to our Microsoft 365 tenant, work that went through thorough security review before it was trusted with production access. Enhancement Three of this capstone reflects the same instinct on a smaller scale: every database write uses a parameterized PreparedStatement specifically so user input can never be concatenated into a SQL string, closing off an entire class of attack before it can happen instead of patching it after the fact.

All three enhancements in this ePortfolio are the same artifact, a Java Contact Service I originally built in CS-320, carried through three different lenses instead of three unrelated projects. Enhancement One turned it from a class only reachable through JUnit tests into a working command-line application and fixed a leaky API design. Enhancement Two replaced its linear, single-structure design with a HashMap and a sorted, binary-searched structure, each chosen for the access pattern it needed to serve. Enhancement Three added persistence through SQLite, so the fast, well-structured application Enhancement Two built doesn't lose everything the moment it closes. Read together, they show one piece of software getting more capable and more secure in stages, which is a closer picture of how software actually improves on the job than three disconnected examples would be.
